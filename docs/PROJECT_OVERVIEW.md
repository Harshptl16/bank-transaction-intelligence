# Bank Transaction Intelligence Platform

**An end-to-end data platform: cloud ingestion → distributed ETL → dimensional warehouse → analytics & BI**

Author: Harsh Patel · Master of Applied Computing, University of Windsor
Target: Winter 2027 co-op applications (Data Engineering / Data Analyst / Business Analyst)

---

## 1. What We're Building

A complete, production-shaped data platform that ingests raw financial transaction data, processes it through a distributed ETL pipeline with PII masking, lands it in a purpose-built dimensional warehouse on Azure, and surfaces business insight through SQL analysis and interactive BI dashboards.

The system is deliberately built in **two layers that each stand alone**:

| Layer | What it is | Who it's for |
|---|---|---|
| **Engineering layer** | Cloud ingestion, PySpark transformation, masking, orchestration, warehouse loading | Data Engineer roles |
| **Analytics layer** | SQL analysis, BI dashboards, business findings write-up | Data Analyst / Business Analyst roles |

The warehouse is the seam between them — the output of the engineering layer and the input to the analytics layer. Nothing is duplicated, but either layer can be led with depending on the role being applied to.

### The one-line pitch

> *"I built the pipeline that gets financial transaction data into a cloud warehouse, then used that warehouse to answer real questions about fraud and customer behaviour."*

## 3. Dataset

**PaySim** — synthetic mobile money transaction data, generated by a simulator built from one month of real financial logs from a mobile money service operating in an African country. Scaled to a quarter of the original size for public use.

**Why PaySim:**
- Realistic transaction structure without real PII exposure
- Widely recognized — recruiters and interviewers know what it is
- Contains a genuine class imbalance problem (fraud is rare), which is realistic
- 30-day simulated window, 744 hourly steps — enough time-series depth for trend analysis

**Raw columns:**

| Column | Meaning |
|---|---|
| `step` | Time unit; 1 step = 1 hour, 744 total (30 days) |
| `type` | CASH_IN, CASH_OUT, DEBIT, PAYMENT, TRANSFER |
| `amount` | Transaction amount |
| `nameOrig` | Originating account |
| `oldbalanceOrg` / `newbalanceOrig` | Originator balance before / after |
| `nameDest` | Destination account (customer `C...` or merchant `M...`) |
| `oldbalanceDest` / `newbalanceDest` | Destination balance before / after |
| `isFraud` | Ground-truth fraud label |
| `isFlaggedFraud` | Flagged by the simulator's own rule engine |

**Known data caveat:** balance columns are zeroed out on fraudulent transactions. Fraud analysis must not treat them as trustworthy signal — this is documented in the dataset itself and is a good example of why understanding source data quirks matters before building on top of it.

## 4. Architecture

```
┌──────────────────┐
│  PaySim raw CSV  │
└────────┬─────────┘
         │
         ▼
┌──────────────────────────┐
│  Azure Blob Storage      │   ← raw container / processed container
└────────┬─────────────────┘
         │
         ▼
┌──────────────────────────┐
│  PySpark transformation  │   ← clean, mask PII, derive columns,
│  (Databricks / ADF)      │      dedupe dimensions, SCD handling
└────────┬─────────────────┘
         │
         ▼
┌──────────────────────────────────────┐
│  Azure Database for PostgreSQL       │
│  (Flexible Server, Burstable B1ms)   │
│                                      │
│   fact_transactions                  │
│   ├── dim_date                       │
│   ├── dim_account (SCD Type 2)       │
│   ├── dim_merchant                   │
│   └── dim_transaction_type           │
└────────┬─────────────────────────────┘
         │
         ├─────────────────┐
         ▼                 ▼
┌────────────────┐  ┌──────────────────┐
│ Analytical SQL │  │  Power BI /      │
│ (15–20 queries)│  │  Tableau         │
└────────────────┘  └──────────────────┘
```

### Warehouse schema (star)

- **`fact_transactions`** — grain: one row per transaction. Carries amount, balances, fraud flags, and FKs to all dimensions.
- **`dim_date`** — derived from PaySim's `step`; hour, day-of-week, month, quarter, weekend flag
- **`dim_account`** — customer accounts, **SCD Type 2** (tracks region/status changes over time)
- **`dim_merchant`** — merchant accounts, separated from customer accounts to mirror real banking schemas
- **`dim_transaction_type`** — the five PaySim transaction types plus a channel category

**Notable design decisions:**
- **Dual destination FKs** — a transaction's recipient can be a customer *or* a merchant, so the fact table carries both `dest_account_key` and `dest_merchant_key` with a `CHECK` constraint enforcing exactly one is populated.
- **Partial indexes** — fraud rows are a small fraction of the table, so the fraud-analysis index covers only `WHERE is_fraud = TRUE`, keeping it small and fast.
- **Partitioning deferred** — the pattern is written but not applied until row-count distribution is measured. Partitioning preemptively without evidence is a common anti-pattern.

## 5. Tools & Technologies

### Core stack

| Category | Technology | Role in the project |
|---|---|---|
| **Distributed processing** | Apache Spark (PySpark) | ETL: cleaning, joins, aggregation, masking, dimension dedup |
| **Cloud storage** | Azure Blob Storage | Raw and processed data landing zones |
| **Orchestration** | Azure Data Factory *or* Databricks | Scheduled pipeline runs, retry logic, failure alerting |
| **Warehouse** | Azure Database for PostgreSQL (Flexible Server) | Dimensional warehouse, analytical query target |
| **BI / visualization** | Power BI (primary) or Tableau Public | Operational and risk dashboards |
| **Language** | Python 3 | ETL logic, orchestration scripts, data generation |
| **Database driver** | `psycopg3` | Batch loading Spark output into Postgres |
| **Version control** | Git / GitHub | Repo, README, documentation |

### Supporting tools

| Tool | Purpose |
|---|---|
| `pandas` | Local exploration and validation before Spark work |
| `pyspark.sql.functions` | Transformation primitives (`sha2`, `when`, `window`) |
| Azure CLI (`az`) | Provisioning server, firewall rules, storage containers |
| Azure Cost Management | Budget alerts to stay inside free-tier credit |
| `pglast` (optional) | SQL syntax validation before applying DDL |

### Why these specific choices

- **PySpark over pandas** — the dataset would fit in memory, but the point is demonstrating distributed-processing competence, which is what the job descriptions ask for. Also forces genuinely different code structure (lazy evaluation, partitioning).
- **Azure over AWS/GCP** — Canadian banks, TD especially, name Azure explicitly in their postings. AWS is the more common general-purpose choice but the wrong one for this target.
- **Postgres over a dedicated warehouse (Snowflake/Synapse)** — builds on existing PostgreSQL depth, keeps cost near zero, and the dimensional modeling concepts transfer directly.
- **Power BI over Tableau** — TD names Power BI directly in multiple postings. Tableau Public is the fallback if licensing is a problem.

## 6. Build Phases

### Phase 0 — Setup & dataset (2–3 days)
Download PaySim, set up Azure free-tier account, configure local Python/PySpark environment, set a spending alert.

**Learn:** scoping a real dataset, recognizing its quirks and limitations before building on it.

---

### Phase 1 — Local exploration (2–3 days)
Profile the dataset in pandas: distributions, null patterns, fraud class balance, cardinality of account/merchant IDs. Decide what region/category values to synthesize for the dimensions.

**Learn:** exploratory data analysis as a design input, not an afterthought.

---

### Phase 2 — PySpark ETL (Week 1)
Read raw CSV, clean nulls and duplicates, standardize formats, **mask account identifiers** (hash `nameOrig`/`nameDest`), derive columns (transaction hour, day-of-week, rolling per-account counts), split destination into customer vs. merchant.

**Learn:**
- Spark DataFrame API and lazy evaluation — why `.select()` is free and `.show()` is not
- Partitioning and shuffle behaviour; why Spark code is structured differently from pandas
- Practical data masking (hashing vs. tokenization vs. redaction) — directly relevant to bank data-governance interview questions

---

### Phase 3 — Azure setup (Week 2)
Provision Blob Storage containers and Azure Database for PostgreSQL Flexible Server (Burstable B1ms). Configure firewall rules and SSL. Build the Data Factory pipeline or Databricks notebook that runs the Spark job on a schedule.

**Learn:**
- Managed database provisioning, tiers, and cost tradeoffs
- Azure networking basics — firewall rules, SSL enforcement (Azure Postgres requires SSL, which will break naive connections until handled)
- Orchestration concepts: triggers, dependencies, retry logic
- **Cost-conscious cloud usage** — deallocating idle resources, budget alerts

---

### Phase 4 — Warehouse build & loading (Week 3)
Apply the star schema DDL to the Azure instance. Load transformed data via batch insert / `COPY`. Implement **SCD Type 2** logic for `dim_account`. Make the pipeline **idempotent** so re-runs don't create duplicates. Run indexing experiments against `fact_transactions` and measure query performance differences.

**Learn:**
- Slowly Changing Dimensions — a core, frequently-interviewed data engineering concept
- Idempotent pipeline design
- Batch loading strategies and upsert logic
- How managed Postgres performance differs from local (connection pooling, cold starts, storage-tier IOPS limits)

---

### Phase 5 — Analytical SQL (Week 4a)
Write 15–20 analytical queries: transaction volume trends, spending patterns by type and merchant category, anomaly detection (sudden spikes, off-hours activity), cohort analysis by account segment.

**Learn:**
- **Window functions** (`LAG`, `ROW_NUMBER`, moving averages) — the single most-tested SQL skill in data analyst interviews
- Translating a vague business question into a concrete query
- Query performance from the analyst's side

---

### Phase 6 — Dashboards (Week 4b)
Connect Power BI to the Azure warehouse. Build two to three dashboards:
- **Operational** — transaction volume, trends, seasonality, channel mix
- **Risk** — flagged anomalies, fraud rate by transaction type, concentration analysis
- Add interactivity: date range, region, account segment filters

**Learn:**
- Dashboard design principles — what belongs above the fold, when a KPI card beats a chart, avoiding clutter
- Power BI itself: data model relationships, DAX basics, connecting to a cloud Postgres source

---

### Phase 7 — Findings & packaging (Week 5)
Write a 1–2 page findings document in plain business language. Write the README with two entry points (engineering-first and analytics-first). Clean repo structure. Push to GitHub.

**Learn:**
- **Business communication** — translating technical work for a decision-maker, which differentiates candidates in DA/BA interviews far more than SQL syntax does
- Packaging a project so a recruiter skimming for 30 seconds gets the point

## Appendix — Interview Talking Points This Project Generates

**On data governance:** why mask at the ETL layer rather than at query time; hashing vs. tokenization tradeoffs.

**On schema design:** why merchants were split from accounts; the dual-FK constraint and its querying tradeoff; why partitioning was deferred rather than applied upfront.

**On Spark:** lazy evaluation; why the dataset would fit in pandas but Spark was still the right choice for the target architecture.

**On SCD:** why Type 2 over Type 1; how re-runs are made safe.

**On cloud:** managed vs. self-hosted Postgres performance differences; cost management on a constrained budget.

**On analysis:** the balance-column caveat in PaySim, and how a data quirk discovered early changed what the fraud analysis could rely on.
